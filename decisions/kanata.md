# kanata

Status. kanata 1.12 from Homebrew and the Karabiner DriverKit VirtualHIDDevice driver 6.2.0 run
as two root daemons on a machine whose `kanata` piece is on, set up by `src/setup-kanata.sh`.
`dotfiles/kanata/DRIVER` pins the pair, kanata is held with `brew pin`, and only
`src/setup-kanata.sh --upgrade` moves the two, together.

## Now

Caps Lock held is Hyper as the four real modifiers and a tap is Caps Lock, Right Option held is
META as shift, control and option, and the top row is the Apple media row with fn for the plain
F keys. Olm listens for both forms of each leader, so it needs nothing from this module, and on a
machine where kanata is not running Caps Lock still reaches Olm as F18.

kanata types through the driver's virtual keyboard, and the two speak an IPC protocol that changed
between driver 6 and driver 8. kanata 1.12.0's release notes say the supported driver is v6.2.0.
kanata pull request 2123, merged 2026-07-28 and first shipped in the 1.13.0 prerelease, moves
kanata to VirtualHIDDevice v8 and says users of the standalone v6.2.0 driver must upgrade the
driver and kanata together. So the pair is a table, `dotfiles/kanata/DRIVER`, one row per kanata
minor version naming the driver version, the package URL on the driver's GitHub release and the
sha256 that release lists. It is the one place either version is written, the way the Neovim
lockfile is. The step picks the row by the installed kanata's minor version and stops when there
is none. It installs the driver only from that URL, only when the download matches the hash,
`pkgutil --check-signature` reports Apple notarization, and the installer certificate belongs to
team G43BCU2T37.

kanata is held with `brew pin`. This is the one exception to the rule that nothing here is
pinned, and the rule now says so. A formula that must move in step with something Homebrew does
not manage is pinned, upgraded only through its module's step, and named with its reason here.
`src/setup-kanata.sh --upgrade` refreshes Homebrew, stops unless `DRIVER` has a row for the
stable kanata, unpins, upgrades with cleanup held back, installs and activates the paired driver,
restarts both daemons, pins again, pinning on a failure too, and reads the grants.

Both daemons are launchd jobs under `/Library/LaunchDaemons`, `mdj-env.karabiner-vhid-daemon` and
`mdj-env.kanata`, `RunAtLoad` and `KeepAlive`, logging to `/Library/Logs/mdj-env`. The plists are
generated by the step from the running user's home directory. kanata runs as
`/Library/Application Support/mdj-env/bin/kanata`, a copy of Homebrew's binary owned by root in
directories only root can write, since the Cellar and anything on PATH belong to the person. The
step asks Homebrew for the source file, never PATH, proves it cannot run commands before copying,
copies it only when its sha256 differs, and proves the copy again, so what was proven is what
runs. The grants belong to that stable path, but the binary is ad hoc signed with its cdhash as
its only requirement, so a new build there may need them given again. kanata is restarted when
the sha256 of the stowed config differs from the one recorded when it last started, when the
copy was replaced, or when its plist changed.

kanata runs as root and reads a config in a checkout its user can write. That is safe only
because this Homebrew build cannot run commands. The step proves it on every run with
`kanata --check` on a config that sets `danger-enable-cmd yes` and binds `(cmd echo hi)`, and goes
on only when kanata rejects it with the note `kanata was compiled to never allow cmd`.

Three grants are declared as gates and answered by `dotfiles/kanata/grants-probe`. The driver
extension comes from `systemextensionsctl list`. Input Monitoring and Accessibility come from
kanata's own log, since kanata 1.12 checks both at startup, in that order, and says what it
found.

## Rejected

- **feetthejim hyperkey.** 2026-10-22. It is F18 plus a tap that stamps the modifiers onto the
  next key, which `decisions/olm-leader-keys.md` already turned down the same day as stamping. A
  tap is blind in a password field, since secure input hides every event tap, and a lost key up
  leaves the modifiers stuck.
- **Karabiner Elements.** 2026-10-22. It is the heavier of the two for one remap, a settings app and
  daemons of its own beside the same driver, and its current release
  ships VirtualHIDDevice v8, which kanata 1.12 cannot talk to, so the two cannot share one driver
  on one machine. Installing it remains outside `docs/PLAN-LEADERS.md` as before.
- **Running kanata and the driver daemon by hand under sudo.** 2026-10-23, after the trial. Phase 0
  of `docs/PLAN-MACHINES.md` found the driver daemon had stopped since the trial, so kanata waited
  ten seconds, released the keyboard and remapped nothing, and nobody noticed. A daemon that
  launchd keeps alive is the only shape that survives a restart or a crash.
- **Leaving kanata unpinned.** 2026-10-23. Setup never upgrades, but a person's bulk
  `brew upgrade` would, and kanata 1.13 with driver 6.2.0 cannot reach the virtual keyboard, which
  leaves the keyboard unremapped until somebody finds out why.
- **The link in Homebrew's bin directory in the kanata plist.** 2026-10-23. It looks stable across
  upgrades, but macOS sees the resolved Cellar path either way, so it buys no grant continuity and
  hides which file was granted. An upgrade moves the path and the grant is given again in both
  cases, and the binary is only ad hoc signed, so a new build would not match an old grant anyway.
- **Running the Homebrew binary itself from the root daemon.** 2026-10-23 10:06, found in review.
  The Cellar belongs to the person, so anything running as them could replace the file and be
  root at the next restart, and resolving it through `command -v kanata` let any directory early
  on PATH decide what root runs. The daemon runs a root owned copy instead, taken from
  `brew --prefix kanata` and proven before and after copying.
- **Copying the config to a root owned path for the daemon.** 2026-10-23, not built. It is the
  plan's answer for a kanata that can run commands, and the step proves this one cannot. It
  becomes the answer the day the proof fails, which the step reports as an error rather than
  starting the daemon.
- **Two grants instead of three.** 2026-10-23. The plan named the driver approval and Input
  Monitoring. kanata 1.12's own source, `src/oskbd/macos.rs`, checks Accessibility right after
  Input Monitoring and refuses to open the keyboard without it, so it is a gate like the others.
- **A hook in `step_if` so the step can speak when its piece is off.** 2026-10-23. Saying that a
  switched off machine keeps its daemons would need every optional step to accept a new mode for
  one note. The step itself says it when run by hand on such a machine, and
  `dotfiles/kanata/AGENTS.md` has the removal commands.

### 2026-10-23 10:06

Review found that the daemon ran a file the person can write. The Cellar path in the plist was
chosen for the grants and ignored ownership, since `/opt/homebrew/Cellar/kanata/1.12.0/bin` is the
person's, and the path came from `command -v kanata`, so PATH decided what root ran. The step now
resolves the source from `brew --prefix kanata`, proves it cannot run commands, copies it to
`/Library/Application Support/mdj-env/bin/kanata` as root with mode 755 when its sha256 differs,
repairs either directory if the person could write it, proves the copy and checks the config with
it, and restarts kanata after a new copy. The plist runs the copy and the grants go to its path.

What a stable path buys for the grants was measured only as far as the signature. `codesign -dv`
on the Homebrew binary reports `flags=0x20002(adhoc,linker-signed)` and `Signature=adhoc`, and
`codesign -d -r-` gives `designated => cdhash H"135f4772..."`, so the binary's only requirement is
its own hash. macOS records the requirement with a grant, so a new build at the same path is
expected to need the grant again, through switching it off and on in both panes. That was not
observed, since it needs a granted binary to replace, and the first upgrade is where it is
measured. The stubbed harness covers a fresh machine, an unchanged one, an edited config, the
upgrade paths, a Homebrew binary changed under the same version, which recopied and restarted
kanata and nothing else, a Homebrew kanata that accepts commands, refused before the copy was
touched, and a kanata planted early on PATH, which was ignored.
