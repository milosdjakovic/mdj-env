## Ordering constraints the root owns

- Several names are forward declared as nil locals near the top of the file (revealHyperLayer, hideHyperLayer, menuSearchSurface, overlayDisplaySurface, enterScope) and only assigned real functions hundreds of lines later, once the predicates table, the contextOverlays seam, or the tools they front for exist. This is not a sibling need between two plugins, it is the root's own within file forward reference discipline, and a reordering that read one of these locals before its real assignment would silently capture nil.
- spoon.CanvasPanel.configure and spoon.Chooser.configure are each called at least twice, once early with a partial options table (surface, then later screen for CanvasPanel; matcher/decorate for Chooser at the point every subsequent Chooser.new call depends on decorate already being installed). The decorate seam specifically must land before the FIRST of the roughly dozen Chooser.new calls anywhere else in the file, which is a constraint on the shared atom's own configuration sequence, not on any one plugin's declared siblings.
- spoon.HyperKey:configure is called twice, once early with chord/trigger/onTap/onHold/onHoldEnd, and again much later with just { predicates = predicates }. The second call must land after the predicates table is fully built but before the final hyperContexts bind loop runs, since that loop's HyperKey:bind calls carry a when name that HyperKey resolves against whatever predicates table it currently holds.
- registry.register(...) must be called for every tool before registry.activate(...) runs, and registry.activate must run before the loop that walks registry.shortcuts(), since shortcuts() only yields entries for tools both registered and active. A tool registered after the shortcuts loop already executed would silently never get its base key bound.
- The queryScopeSpec list order is semantically load bearing for alias collisions: 'QueryScope gives a colliding alias to whichever scope claims it first, so this order decides who owns a word.' This is a property of the composition root's own array, with no natural expression as a per plugin sibling declaration, since it is about which of two UNRELATED plugins wins a naming collision based purely on list position.
- The choosers list order (registry.surfaces({ "clipboard", "caffeinate", "vpn", ... })) decides which surface answers activeChooser() if two ever report isShowing() true at once. 'the order decides the answer if two are ever up at once, and nothing in this tree proves they cannot be.' Again a total order over the whole set, not a pairwise relationship any manifest field captures.
- windowLeaderCode is resolved once and stamped onto a shallow copy of every keys.windowManagement entry before that single stamped copy is handed to both spoon.WindowManager:bindToLeader and spoon.WindowCheatSheet:configure. Both consumers must receive the identical already stamped table; independently stamping two copies, or stamping after one consumer already read the unstamped data, would let dispatch and the overlay silently disagree about which physical key is the window leader.
- spoon.ChordKey:start() is deliberately the last of the three leader engine calls, run only after both spoon.HyperKey:start() and spoon.WindowLeader:start() have registered their keys into it: 'Every active leader is now registered; start the one shared event tap that drives HYPER and the window leader together.' Starting the shared tap before every leader has registered would mean the tap runs with an incomplete key set.
- spoon.QueryScope's own scope table is assembled after spoon.Emoji has already been configured and has already chosen a backend, because building that table asks spoon.Emoji:lists() once, synchronously, to decide whether an emoji scope exists at all. This is a real dependency of one plugin's CONFIGURE TIME behavior on another plugin's configure having already run, not on its declared siblings or tools.
- The registry.register block for menuSearch, and everything downstream that reads it (registry.shortcuts, queryScopeSpec), sits after MenuSearch:configure() has assigned openBuiltinMenuSearch, menuSearchSurface, scopeMenuRows, and scopeMenuRun onto what were forward declared nil locals. Moving the registration earlier would capture those locals while they still held nil, silently and permanently.
- filePreviewProvider and filePeekProvider are chosen once at the very top of the file specifically because 'the bindings depend on them,' yet FileSearch itself is not configured until roughly 1700 lines later. The bindingNeeds table and bindingApplies filter built from that early choice are read by every later call to footerFor and rowsFor, long before FileSearch exists, which means the policy decision and its principal consumer are separated by nearly the whole file with only shared upvalues bridging them.
- rowsFor is defined long before spoon.Olm.registry is assigned (spoon.Olm.registry = registry runs far below rowsFor's own definition), and the code deliberately reads spoon.Olm.registry through the global at CALL time rather than capturing the local registry, exactly to survive being defined before its dependency exists. An apply step that tried to inline or pre resolve that reference at definition time would break this.
- Two separate binding loops exist for two different purposes and must not be conflated or reordered relative to each other: the registry.shortcuts() loop binds each ACTIVE, REGISTERED tool's own OPEN key (leader or global), while the later loop over keys.hyperContexts binds the IN LIST navigation keys (j, k, i, x, and the rest) for every context regardless of whether that tool went through the registry. A few tools (the launcher, menu search) still bind their open key directly rather than through the registry loop, so the two mechanisms are not yet fully unified in the live root.
